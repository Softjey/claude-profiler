**Verify command:** `pnpm verify` → **40 files, 379 tests, all green**. Plus `buildProfile`
over three real transcripts of different sizes and models, re-asserting the stage sum
against `timeline.modelMs` on each.

**An earlier run of this record verified in a detached worktree**, because the working tree
then held unrelated in-flight work that made `pnpm verify` red (`extractBashGroup is not a
function`, a `ToolDetail.tsx` prop mismatch). That work has since landed and the tree is
green, so the numbers above are from an ordinary run. T18 touches none of those files.

**The exact measurement was rejected on measured grounds, not assumed ones.** The
`MessageDisplay` hook records `firstFlushAt` — the first visible token, which is exactly the
prefill boundary — and `message.id` in the transcript joins to its `message_id`. It was
built and then removed. Cost of one invocation of the built hook script, 40 sequential runs
writing real sidecar lines: **0.846s wall, ~21ms each**, of which a bare `node -e 0` is
~19ms. It fires once per streaming flush, so a session producing 200k output tokens spawns
thousands of processes, on every turn the person runs, to sharpen one row of one table and
only on sessions recorded with it. Declined; the `messageId` and `firstFlushAt` plumbing was
stripped back out rather than left dormant.

**The fit is honest about being a fit.** Three coefficients were tried
(`totalMs = a + b·contextTokens + c·outputTokens`). Over one real session's two halves the
token slope moved 104.8 → 107.3 tok/s, while `a` went +5.62s → −8.13s and `b` went
−13.8 → +38.0 ms per 1k tokens — both flipping sign. Only the slope survives, which is why
waiting is a residual rather than a prediction, and why the half-spread is computed at
runtime and shown to the user.

**The stability threshold was revisited, as predicted, on first use.** This record
originally called the 25% half-spread gate "the number most likely to need revisiting". It
needed it immediately: a third session (`311e733d`, 230 requests, sonnet-5) measured
**26.0%** and was refused, which swapped the whole drill-down for a different table with
different row names over a one-percentage-point difference. Real spreads so far are 2.3%,
23.9% and 26.0% — clustered right on the line, so the line was deciding two of three
sessions arbitrarily. The gate is gone; the spread is now printed beside the rate and the
reader weighs it. Only the structural gates remain, where there is genuinely no rate to
report.

**The drill-down is now one table, not two.** It showed the estimate stacked above the
measured grid, which asked the reader to reconcile two answers to the same question. The
grid is the fallback for when no rate can be fitted, and stays in the JSON artifact under
`modelBreakdown.phases` either way.

**What is still an estimate, plainly.** Every row. Thinking is the firmest because
`thinkingTokens` is a measured number from the request's own `usage` and only the multiplier
is fitted. Generating is thinking's sibling under the same multiplier. Waiting is the
leftover and therefore absorbs every error in the rate — on `5181d732`, 10 of 183 requests
had predicted generation exceed their own wall-clock and were clamped to zero waiting. That
count is carried in the artifact as `modelStages.clampedRequests`; it is no longer on screen,
which is the cost of the one-line note the drill-down now carries.
